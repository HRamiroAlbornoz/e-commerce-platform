# Design System: CLACK

## Overview

**Creative North Star: "The Numbered Specimen Case"**

CLACK's shipped catalog is a flat grid of specimens: every product sits inside its own full-bleed field of color, badged with a piece number, and described underneath in two weights of type — a didone name/price and a grotesque description. It is the teletext half of the direction contract's museum thesis: the closed four-color field, the numbering, and the didone/grotesque split all shipped exactly as specified. The catalog's search field and category rail — described in the surface brief's FIRST VIEWPORT — have also shipped, as a filter strip on the catalog route rather than fused into the shared header markup (see Navigation / Header). The cartela and its dotted spec table have also shipped — but as a standalone product detail page reached from a card, not as the split-hero composition the brief originally described. Slice 5 added the account-facing surfaces (register, login, forgot-password, Google sign-in, logout, and an admin-access-denied state); it introduced no new color, typeface, or elevation model — it is the same teletext-museum world applied to a fourth kind of screen, plain form pages sitting directly on the page's own theme-swapping ink/bone ground. Slice 4 added pagination to the catalog listing (`PaginationControls`, see Components): a pure application of the existing system — the `Button` primitive, the hairline-divider vocabulary, and the established 70%-opacity support-text pattern — with no new color, typeface, spacing, or elevation token introduced to build it. Slice 6 added the cart surface (`CartPage` at `/cart`, reached through the existing `PublicLayout`): a single receipt-style list of `CartLineItem`s, each carrying its own closed-four-color stripe, the reusable `QuantitySelector`, and a tabular-nums line total, closed by a running total — the same world applied to a fifth kind of screen, sitting on the page's own theme-swapping ground like the auth pages, not a fixed-tone cartela. It introduced no new color, typeface, or elevation token; its one structural extension is applying the dotted-rule divider — previously scoped to the cartela's spec table — to a second context, an itemized receipt-style list (see Shapes). It also added a quick-add affordance to the Product Card itself, restructuring the card from a single full-card `<Link>` into a `<div>` wrapping a `<Link>` plus a sibling action row (see Components). Slice 7a added the checkout stepper (`CheckoutPage` at `/checkout`, inside `PrivateLayout`/`ProtectedRoute`): the cart and its three steps — Envío, Pago, Revisión — render as one continuous growing document, never a per-step screen swap or modal, with a perforated (`divide-dotted`) rule separating each completed step section (the cartela's spec-table divider, and the cart's line-item divider, now confirmed a third time in a third context). Its one genuinely new decision is resolving the base-breakpoint pinning the direction contract had explicitly left open for this surface: the step indicator becomes `sticky top-0` and the running total becomes `fixed inset-x-0 bottom-0` at the base/mobile breakpoint only, both opaque and hairline-bordered, both resetting to normal in-flow layout at `md:` (see Layout and Do's and Don'ts). It also extracted `CartLinesSummary`, a shared cart-lines-plus-total block now used by both `CartPage` and `CheckoutPage` (see Components), and gave `Button` an exported `BUTTON_CLASSES` constant so a plain `<Link>` styled as a button doesn't have to retype the primitive's classes (see Button, under Components). No new color, typeface, or elevation token was introduced. The payment step deliberately does not collect a card number, expiry, or CVV — only a cardholder name and an explicit "Resultado simulado: Aprobado/Rechazado" choice, with copy stating no real charge occurs; this is a scoped content-model simplification, not a missing field. The review step's "Confirmar compra" button is intentionally inert — no `onClick` — because order creation is deferred to a future slice, the same disclosed pattern the product detail page's "Agregar al carrito" button followed for several slices before it was wired. Slice 8 added the private order-history surface: `OrdersPage` (`/orders`) and `OrderDetailPage` (`/orders/:orderId`), both inside `PrivateLayout`. It reuses the exact `max-w-2xl`, hairline-divided single-column family already established by `CartPage`/`CheckoutPage`, and the `divide-y divide-dotted` list vocabulary for both the order list and an order's line items — a fourth and fifth context for that divider, after the spec table, the cart, and checkout's step sections. It introduced this project's first overlay primitive, `Modal` (see Components), built for reuse from the outset — three more destructive-confirmation flows were already planned (a review's own delete, an admin's hard-delete, an admin's order cancellation) when it shipped — flat, hairline-bordered, no shadow, matching the Flat Ground Rule even for an element that finally sits above the page instead of in its flow. `OrderStatusBadge` distinguishes the four order states by text and typographic treatment (outline / outline+underline / filled / outline+strikethrough), never by color alone. No new color, typeface, or elevation token. Slice 9 added reviews and ratings, reached from the cartela's existing rating-summary link. `ProductReviewsPage` (`/products/:id/reviews`) joins the same single-column, hairline-divided, `divide-dotted`-list family. It extracted two shared primitives out of slice 8's one-off `CancelOrderModal`: `ConfirmActionModal` (a `Modal`-backed confirm/cancel shell with its own async submit state) and `DestructiveTriggerButton` (the underlined text control that opens one) — both now shared between `CancelOrderModal` and this slice's own `DeleteReviewModal`. `RatingDisplay` reads a 1-5 rating as five square segments with the number spelled out beside them, the same zero-icon, non-color-only convention as `OrderStatusBadge` applied to a numeric scale. `RatingInput`, the form counterpart, is `Controller`-driven rather than `register()`-bound, because `react-hook-form`'s own uncontrolled-radio sync silently fails to pre-check a numeric field's matching option. `Textarea` joins `TextField` as this system's second labeled-input primitive, sharing its bare-bottom-border language and hint/error-slot behavior through an extracted `useFieldDescribedBy` hook. No new color, typeface, or elevation token. At this point in the build there was still no hero or landing composition anywhere on the site — that gap wasn't closed until slice 14, whose own paragraph closes out this section below. Slice 10 added the first administration surface (`/admin/products`, inside `AdminLayout`/`AdminRoute`): a dense, real `<table>` of the full product catalog with price and stock editable directly in the cell, retire/reactivate and hard-delete actions per row, and a full-form create/edit route. It is the first surface built in **Operate mode** rather than the public/private surfaces' specimen-case register — density and repetition speed outrank the catalog's editorial identity here, per the admin surface brief (`.impeccable/surfaces/src-routes-admin-adminlayout-tsx.md`). It inherits the palette and type wholesale (no new color, typeface, or elevation token) but "baja el volumen a propósito," per the brief's own words: the per-product color field shrinks to a `size-4` thumbnail in the first column instead of a full field, and grotesque (Archivo) carries the whole surface except the didone (Bodoni Moda) screen title. See Admin Products Table, Editable Number Cell, Product Status Badge, and Admin Product Form, under Components. Slice 11 replaced that form's free-text "URL de la imagen" field with a real upload: `ImageUploadField`, this project's first native file input and first progress bar, built on already-established primitives — the bare-bottom-border input language, `InlineError`, the field-color accent (magenta light / cyan dark) — rather than any new visual token. See Image Upload Field, under Components. Slice 12 added the second administration surface, `/admin/orders` (F11): the full order list, filterable by status, with per-row status-transition controls that move an order through `ORDER_STATUS_TRANSITIONS` (pending → processing/cancelled, processing → completed/cancelled, completed/cancelled → nothing). It is a straight reuse of slice 10's "the table is the screen" shape — a real `<table>` at `md:` and up, the same stacked-card-with-inline-labels fallback below it, the same `TABLE_LABEL_CLASSES` — with one deliberate divergence from its sibling: the status filter lives in the URL (`?status=`), not client-only state, per F11.2's explicit requirement, unlike `AdminProductsPage`'s client-side category/name filter. This slice resolved `AdminLayout`'s own previously-recorded deferral: with a second admin section now shipping, the nav rail ("Productos" / "Órdenes") described as speculative scaffolding in slice 10 is now built (see Admin Layout, under Components). It also generalized three pieces built for a single consumer into genuinely shared ones: `TableSkeleton` (replacing two byte-identical skeleton components, one per admin table), `TABLE_LABEL_CLASSES` (relocated to `src/features/admin/constants/`, now shared by both admin sub-features instead of living under `products/`), and `CancelOrderModal`, which traded a `user` prop plus an internal `cancelOrder` call for an injected `onCancel: () => Promise<Result>` action so both the customer's own order-detail cancel flow and this slice's admin row can supply their own cancellation call through the identical modal. `DestructiveTriggerButton` gained a `disabled` prop and now exports its class string as `TEXT_ACTION_BUTTON_CLASSES`, reused as-is (not re-skinned) by the row's non-destructive forward-transition buttons ("Marcar en proceso", "Marcar completada") — the same underlined-text-control language, applied to a same-visual, not-destructive sibling action, not a new button style. No new color, typeface, spacing, or elevation token was introduced to build any of it. Slice 13 added the third administration surface, `/admin/analytics` (F12): a single sales-summary page — total revenue and order count, plus a top-five-products-by-units-sold chart — reached from a third entry ("Analytics") in `AdminLayout`'s nav rail alongside "Productos"/"Órdenes". The only change to `AdminLayout` itself was adding that one entry to `ADMIN_NAV_LINKS`; the nav rail's own markup, built in slice 12, was otherwise untouched. The whole page is gated on one Firestore aggregation query (`useOrdersSummary`, a single `sum('total')` + `count()` over non-cancelled orders): when `totalOrders` is 0, the page renders a single `EmptyState` ("Todavía no hay ventas") in place of everything else, never a page with empty tiles and an empty chart underneath — the same empty-vs-content gate the rest of the system already draws at the page level rather than per-widget. It also introduces this project's first chart, `TopSellingProductsChart`, built with Recharts (`recharts@^3.10.1`, this project's first charting dependency) — every Recharts color prop (`Bar fill`, `LabelList fill`, axis `tick.fill`, axis/grid `stroke`) is `currentColor`, so the chart inherits the page's own ink/bone theme-swap with no chart-specific color token added to the palette, and each bar's exact value is drawn directly on the bar via `LabelList` rather than left to a hover-only tooltip, so no series depends on color or interaction alone to be read. Its summary numbers, `AnalyticsSummaryTiles`, deliberately do **not** use a boxed metric-card layout: an early draft did (a two-cell bordered grid, each cell reading as its own card), and it was caught during the `impeccable polish` pass as exactly the "hero-metric template" the admin surface's own direction contract THESIS rejects by name ("Rechaza el panel de administración que imita un dashboard de producto —tarjetas de métricas, gráficos decorativos, aire de sobra—"). The shipped version instead reuses this project's own established idiom for a small set of totals — `OrderDetailPage`'s flowing `<dl>` plus a `border-t` hairline and a label/value pair, not a card — applied here to a second `<dl>` of totals (see Analytics Summary Tiles, and the new Do below). No new color or typeface token was introduced; `TABLE_LABEL_CLASSES` (slice 10/12) carries both the tiles' `<dt>` labels and the chart section's own heading, and `formatPrice` (already shared by the cart, checkout, and order pages) formats the revenue figure — reused, not duplicated. Slice 14 finally closed the hero/landing gap flagged since slice 9 (F14): rather than a separate landing route, `CatalogPage` (still mounted at `/`) gained a `FeaturedProductHero` section rendered above its existing filters/grid — the home page is hero-plus-catalog on one continuously-scrolling page, not two screens. The featured product is the catalog's own most-recently-created active item (`getFeaturedProduct`, a dedicated `where('isActive','==',true), orderBy('createdAt','desc'), limit(1)` query reusing the same composite index the catalog's own unfiltered query has used since slice 2), resolved by its own `useFeaturedProduct` hook — deliberately independent of `useActiveProducts`, so a slow or failed fetch on one never blocks the other, the same two-independent-queries reasoning slice 13's analytics page already established (an alternative that derived the featured product from the catalog query's own first result was evaluated and rejected, specifically because it would couple the hero's stability to the grid's own loading/filter state). On the default view (no filter, no search, page 1) the featured product is excluded from the grid below it so it never shows twice; under an active filter or search it can legitimately reappear (see Featured Product Hero, under Components, and the new Do below). The hero reuses `AddToCartControl` and `formatPrice` unmodified, and its text panel is `bg-bone text-ink` unconditionally — a second confirmed instance of the Fixed Paper Rule (see Colors), a deliberate divergence from slices 5/6/7a's choice to stay on the page's own theme-swapping ground, made because the hero presents the same specimen-as-paper-object content (name, curatorial note, price, add-to-cart) the cartela already established, not a login form or a receipt. No new color or typeface token was introduced; the one new shared token is `PRODUCT_IMAGE_FRAME_HEIGHT_CLASSES`, extracted from `ProductDetailPage`'s own image-frame class string during this slice's `/simplify` pass — but the hero does **not** consume it, because the hero's own mobile height needed to cap rather than only floor (see Featured Product Hero, under Components, and the new Do below). This document records what was actually built.

Depth is never simulated. There are no shadows, no gradients, and no border-radius anywhere in the sampled components — flatness is total, not partial. The dark theme (ink ground, bone text) is primary; the light theme is currently a literal swap of the same two neutrals rather than a separately-designed surface (see Do's and Don'ts). The cartela is the one deliberate exception to theme-swapping altogether: it stays bone/ink regardless of the active theme (see the Fixed Paper Rule, under Colors). The auth screens shipped in slice 5, the cart surface shipped in slice 6, and the checkout stepper shipped in slice 7a all deliberately did **not** extend that exception — they use the page's own swapping background, not a second fixed-tone panel (see AuthPageLayout, CartPage, and CheckoutPage, under Components). The catalog's featured-product hero, shipped in slice 14, is the opposite case: it **does** extend the exception, deliberately, because it is a second specimen-label surface rather than a form or a receipt (see FeaturedProductHero, under Components, and the Fixed Paper Rule).

**Key Characteristics:**
- Closed four-color field system (lime, magenta, cyan, amber) — flat, full-strength, no tints or intermediate variants.
- Didone (Bodoni Moda) carries the single most important line on a view; grotesque (Archivo) carries everything else.
- Zero elevation: no shadows, no gradients, no border-radius anywhere in the system.
- Skeletons mirror the exact shape of loaded content; no spinners.
- Interactive accent color is theme-owned: magenta in light mode, cyan in dark mode, never a fixed hover color — except the fixed-tone surfaces (the cartela, and — as of slice 14 — the catalog's featured-product hero), which never theme-swap at all.

## Colors

Four named, flat, equal-weight fields carry product identity; two neutrals (ink and bone) carry everything else. There is no single "brand primary" hue — the four fields function as a closed set, each one interchangeable in role.

### Primary
- **Field Lime** (`#cfef00`): full-bleed background of a product's image tile. One product, one field, no blending with the other three.
- **Field Magenta** (`#ff3fa6`): same role as Field Lime; also the light-theme interactive accent (link hover/focus, active category chip, and now the auth forms', cart's, and checkout's button/link hover-focus states, including the checkout step indicator's active-step underline and its completed-step edit buttons).
- **Field Cyan** (`#00d9e0`): same role as Field Lime; also the dark-theme interactive accent (link hover/focus, active category chip, and now the auth forms', cart's, and checkout's button/link hover-focus states, including the checkout step indicator's active-step underline and its completed-step edit buttons).
- **Field Amber** (`#ffb100`): same role as Field Lime.

### Neutral
- **Ink** (`#0d0d0c`): dark-theme background; light-theme text. Also the fixed text color of the cartela panel on the product detail page, and — as of slice 14 — the featured-product hero's text panel, in both themes.
- **Bone** (`#f1ecdd`): light-theme background; dark-theme text. Warm off-white, not pure white. Also the fixed background color of the cartela panel, and — as of slice 14 — the featured-product hero's text panel, in both themes.

### Named Rules
**The Closed Four Rule.** Only these four hexes exist as field colors anywhere in the system (enforced at the data layer by `PRODUCT_DISPLAY_COLORS` in `shared/schemas/product.ts`). No tints, no opacity variants, no fifth color. A new field color is a palette decision, not a per-screen choice.

**The Theme-Owned Accent Rule.** The interactive accent is never a fixed hardcoded hue: it is magenta in light mode and cyan in dark mode (see `ErrorState`'s retry link, the active category chip in `CatalogFilters`, the "Agregar al carrito" button's hover/focus on the product detail page, `Button`'s and `TextField`'s focus/hover states, the "¿Olvidaste tu contraseña?" and "Volver a iniciar sesión" links, `AuthNav`'s links, the Product Card's quick-add button, `CartLineItem`'s "Quitar" control, `MergeExclusionsNotice`'s "Entendido" control, and — as of slice 7a — `CheckoutStepIndicator`'s completed-step edit buttons and active-step underline, and every `CheckoutSummaryCard`'s "Editar" control). Amber and lime are identity fields only and never carry interaction state.

**The Cycled-Not-Identity Rule.** The four field colors are a rhythm device, not a per-item unique key, anywhere they're reused as a small swatch. `displayColor` cycles across product tiles (and also fills the image panel on the product detail page and the featured-product hero, and the `w-1` color stripe on each `CartLineItem`, sourced from the same product record, not a new per-line assignment), and `CatalogFilters`' category-rail dot cycles across the six categories (`PRODUCT_CATEGORIES[index % 4]`) the same way — with only four colors and six categories, two pairs necessarily repeat (Teclados/Sillas both lime, Mouse/Mousepads both magenta). This is intentional: the dot is a scan cue, and the uppercase label is the actual disambiguator. Don't "fix" a repeated swatch color by adding a fifth hue — that would violate the Closed Four Rule to solve a problem the system doesn't have.

**The Fixed Paper Rule.** The product detail page's cartela panel (`bg-bone text-ink`) is bone-on-ink **unconditionally** — it does not theme-swap with the page's dark mode, unlike every other surface in the system. It is "papel hueso, como único plano claro": a fixed paper object sitting in the scene regardless of the room's lighting. Any component placed inside a fixed-tone surface like this one must not assume the page's theme-swap applies to it — see the QuantitySelector note under Components. This rule is scoped to the cartela; it does not license a second fixed-tone surface elsewhere without a matching editorial reason. **Confirmed by slice 5, again by slice 6, and again by slice 7a:** the auth screens, the cart page, and the checkout page all had the same choice available and did not take it — `AuthPageLayout`, `CartPage`, and `CheckoutPage` all sit directly on the page's own `bg-bone dark:bg-ink` ground, no bone-fixed panel, even where they pin chrome to the viewport edge (see the Pinned Chrome Rule, under Layout) — pinning is a position change, not a fixed-tone-surface change, and the pinned step indicator and total still theme-swap normally. That is the rule working as intended, not an inconsistency. **Slice 14 is the rule's first genuine second instance:** `FeaturedProductHero`'s text panel is also `bg-bone text-ink` unconditionally, with no `dark:` variant — unlike the auth/cart/checkout pages above, it *does* take the fixed-tone option, because it presents the identical kind of content the cartela already earns it for (a product's name, its curatorial note, its price, its add-to-cart control), not a form or a receipt; it is, in effect, a second small cartela for the room's featured piece. Its own interactive control (`AddToCartControl`'s `QuantitySelector`) is already `border-current`-safe for exactly this reason (see the Quantity Selector note). This is a confirmed extension of the rule, not drift: a fixed-tone surface is still earned by the same editorial logic — a physical paper specimen label — just applied a second time, to a second specimen-shaped surface, not licensed for use anywhere a form or a list would do just as well.

## Typography

**Display Font:** Bodoni Moda (with ui-serif, serif fallback)
**Body Font:** Archivo (with ui-sans-serif, sans-serif fallback)

**Character:** A didone/grotesque pairing borrowed from print editorial — Bodoni Moda's high-contrast strokes read as the "headline of the moment," while Archivo's even, data-journalism grotesque carries labels, descriptions, and supporting copy.

### Hierarchy
- **Display** (400, 1.125rem–2rem, 1.2 line-height): Product name, product price, and the single headline of an empty/error state. On the product detail page the name grows to a 3xl `h1` and the price to `text-2xl` — both still Display, just sized up for the single-item context. **As of slice 14**, `FeaturedProductHero` reuses the identical sized-up treatment for its own product name (`h2`, `text-3xl`) and price (`text-2xl`) — not a new size step invented for the hero, the same values the cartela already established for a single featured specimen. On the auth pages, the same role sizes to a 3xl `h1` for the page title ("Iniciar sesión", "Crear cuenta"). On the cart page, it carries the "Carrito" `h2` title, each `CartLineItem`'s product name and line total, and the running total's amount — the same name+price pairing per row the Product Card already established, not a new doubling. On the checkout page (slice 7a), it carries the "Checkout" `h2` title and, per section rather than per page, each step's own headline: `ShippingForm`'s and `PaymentForm`'s `<legend>` ("Envío", "Pago"), each `CheckoutSummaryCard`'s title, and `ReviewSection`'s "Revisión final" — several Display strings coexist on the one continuous document, but each still belongs to its own component and is still the single highest-weight line within it, so the One Headline Rule (below) is satisfied per-section, not violated by the page as a whole. On all three admin screens ("Productos", "Órdenes", and — as of slice 13 — "Analytics"), it carries only the `h1` screen title — Archivo carries every cell and control in the table itself (see Admin Products Table, Admin Orders Table). The Analytics screen is the one admin page where Display also appears a second time below the `h1`: `AnalyticsSummaryTiles`' two `<dd>` values ("Ingresos totales", "Cantidad de órdenes"), each its own component with its own single Display line, the same per-component scoping the checkout page's step sections already established. Never used for more than one headline-weight string per component.
- **Body** (400, 0.875rem, 1.4 line-height): Product descriptions (clamped to one line in the grid, full-length on the detail page), the curatorial note (italicized, see Components — reused verbatim, unstyled-changed, by `FeaturedProductHero` as of slice 14), the dotted spec table, state-message support text, the catalog search input's typed value/placeholder, and every `TextField` input's typed value, its hint/error text, and form body copy ("Ingresá tu email y te enviamos un enlace..."). A smaller `text-xs` cut of this same 70%-opacity support-text pattern — not the Label token — also carries `PaginationControls`' "Pagina {n}" caption, `CartLineItem`'s "c/u" unit-price line, `MergeExclusionsNotice`'s body text, `PaymentForm`'s "Pago simulado: no se procesa ningún cargo real" disclosure line (slice 7a), and `AdminOrderRow`'s date/client cells (slice 12), matching `TextField`'s hint sizing/color exactly. The checkout summary cards' and review section's confirmed-value lines (shipping address, payment outcome, "Revisá el envío y el pago arriba...") use the same Body family at 80%-opacity ink/bone, one step darker than the 70%-opacity support-text cut, for confirmed data the user already entered rather than incidental supporting copy. **As of slice 13**, `TopSellingProductsSection`'s own empty-ranking fallback text ("Todavía no hay unidades vendidas para armar el ranking") reuses the same `text-sm`/70%-opacity Body treatment, and the chart's own axis labels (product names, unit counts) render in Recharts' SVG `<text>` rather than an HTML element, but are still Archivo — the chart's wrapping `<div>` sets `font-sans` via the page's own body font stack, and every Recharts text prop uses `currentColor`, so the axis type matches the system's Body font and theme without a bespoke font declaration inside the chart. **As of slice 14**, `FeaturedProductHero`'s own "Ver el resto de la sala" anchor is a `text-sm` Body link, styled identically to the product detail page's reviews link, not a new link treatment.

### Named Rules
**The One Headline Rule.** Bodoni Moda appears at most once per component as the highest-weight line — the product name, the price, or a state's message title — never for two competing strings on the same card or screen. **Disclosed exception:** the product detail page has two `<h1>` elements on the DOM — `PublicLayout`'s header wordmark and the cartela's product-name heading — because a single-item detail page earns its own real page heading rather than borrowing the site wordmark's. This is an accepted trade-off, not an error; the header wordmark is a candidate for demotion to a non-heading element the next time `PublicLayout` is touched, but that is out of scope until then. The auth pages hold to the strict rule (one `h1`, `AuthPageLayout`'s own title) since `AccessDeniedState` — the other slice-5 screen that also renders `SiteHeader` — demotes its own heading to `h2`, keeping the wordmark as the page's only `<h1>`. `CartPage` follows the same precedent: its "Carrito" title renders as an `h2`, not an `h1`, keeping `SiteHeader`'s wordmark as the page's only heading — a finish-review finding on that build (it originally shipped with a duplicate `h1`) fixed and verified before ship, confirming the rule a third time rather than becoming a fourth instance to fix later. `CheckoutPage` follows it a fourth time: its "Checkout" title is also an `h2` under `PrivateLayout`'s own header. **A distinct, resolved question for slice 7a:** because the cart-plus-checkout surface is one continuous document, several Display-weight strings (each step's own title) appear on the page at once. This does not violate the rule — the rule is scoped per component, and each step section (`ShippingForm`, `PaymentSummary`, `ReviewSection`, etc.) is its own component with exactly one Display headline inside it. Don't read "one Display string per page" into this rule; read it as written, "one per component." **Slice 13's `AdminAnalyticsPage`** follows the same per-component scoping: its own `h1` ("Analytics") is the page's only heading-weight string, and `AnalyticsSummaryTiles`' two `<dd>` values are each their own component's single Display line, not a second headline competing with the `h1` — the same reasoning already established for checkout's step sections. **Slice 14 confirms it a fifth time:** `CatalogPage` has no `h1` of its own — `SiteHeader`'s wordmark remains the page's only `<h1>`, unchanged — and `FeaturedProductHero`'s own product name renders as an `h2`, the same heading level every `ProductCard`'s own name already uses in the grid below it, not a new heading-level decision.

## Layout

Mobile-first with exactly two upward breakpoints, `md` (768px) and `lg` (1024px); `sm`, `xl`, and `2xl` are not used anywhere in the codebase. The product grid is `grid-cols-1` at base, `md:grid-cols-2`, `lg:grid-cols-4`, with a `1.5rem` horizontal gap and `2.5rem` vertical gap — the vertical gap is wider than the horizontal one so rows read as distinct specimens rather than a continuous mat. Cards are `aspect-square` image tiles with `2rem` of inset padding around the product photo, followed by a `1rem`-gap text stack. State screens (empty, error) center their content with `6rem` of vertical padding, deliberately more generous than the card rhythm. The catalog's filter block stacks search-then-rail with a `1.25rem` gap and sits `2.5rem` clear of the grid below it (`mb-10`); the category rail itself scrolls horizontally on overflow rather than wrapping, keeping it a single scan line. When results span more than one page, `PaginationControls` closes the grid off the same way the filter block opens it: a `mt-10 pt-6` hairline top rule (`border-t border-ink/15 dark:border-bone/15`), with "Anterior"/"Siguiente" `Button`s flanking the page label in a `flex justify-between` row — no new spacing token, the same `2.5rem`/`1.5rem` rhythm reused as a closing bracket instead of an opening one. It's rendered only when there's more than one page of results; on a single page it doesn't render at all. **As of slice 14**, this whole filters-plus-grid-plus-pagination block sits inside a `<div id="catalogo">` wrapper below the featured-product hero (see Featured Product Hero, under Components) — purely a scroll-anchor target for the hero's own "Ver el resto de la sala" link, not a layout or spacing change; the block's own internal rhythm (the values above) is unchanged.

The product detail page is a two-column grid (`grid-cols-1 md:grid-cols-2`, collapsing to one column below `md`): an image panel on the left and the cartela panel on the right. The image panel is `min-h-96` (mobile) / `md:min-h-144` (desktop), with the field color filling it edge-to-edge (a sangre) and the product photo inset via flex-centering (`p-12`) rather than the grid card's fixed padding. The cartela stacks its content with a `gap-4` flex column and pushes price/quantity/cart-button to the bottom of the panel with `mt-auto`, the same bottom-alignment device the grid card uses for price.

The auth pages (`AuthPageLayout`) are a single centered column, `max-w-md`, `px-4`, with generous vertical padding (`py-16` mobile / `md:py-24`) — no grid, no two-column split; a narrower, denser rhythm than the catalog/detail pages because the content is a single form, not a specimen or a gallery. Its title and content area are separated by a hairline top rule (`border-t border-ink/15 dark:border-bone/15`) with `pt-8`, the same hairline-divider language used for the header and the filter block, just applied vertically inside a form page rather than between page sections.

The cart page (`CartPage`) is also a single centered column, `max-w-2xl`, `px-4 md:px-8`, `py-10 md:py-16` — wider than `AuthPageLayout`'s `max-w-md` because a receipt list needs more horizontal room than a form field, but the same single-column, no-grid family. Its title and content area share the identical hairline-divider pattern as `AuthPageLayout` (`border-t border-ink/15 dark:border-bone/15`, `pt-8`). Line items stack inside a `divide-y divide-dotted divide-ink/30` list (see Shapes) rather than the grid's card rhythm, and the running total closes the list with its own hairline rule — the same "closing bracket" device `PaginationControls` uses to close the catalog grid.

**The checkout page (`CheckoutPage`, slice 7a)** shares the cart page's `max-w-2xl` single-column family (it reuses the cart's own line-items-plus-total block, `CartLinesSummary` — see Components) and adds a two-region layout below it once the cart has at least one line: a step-indicator column and a step-sections column, `flex-col` on mobile and `md:flex-row md:gap-12` on desktop, divided from the cart block above by a `md:border-t md:border-ink/15 md:pt-8` hairline that only applies at `md:` and up (at the base breakpoint the sticky step indicator supplies its own visual break instead — see the Pinned Chrome Rule below). The step sections themselves sit inside a `divide-y divide-dotted divide-ink/30` column (see Shapes) — the cartela's spec-table divider and the cart's line-item divider, now reused a third time for a third kind of list: sequential document sections rather than tabular rows or receipt lines. Each section carries `pb-10` and, via `not-first:pt-10`, adds top padding only when it isn't the first visible section, so a single visible step (e.g., before Envío is submitted) doesn't carry a stray leading gap.

**All three admin screens (`AdminProductsPage`, slice 10; `AdminOrdersPage`, slice 12; `AdminAnalyticsPage`, slice 13)** share one layout shell, `mx-auto max-w-6xl px-4 py-10 md:px-8 lg:px-12` — wider than any public/private surface's `max-w-2xl`, because a dense operational screen needs more horizontal room than a receipt or a form. A `flex items-center justify-between` header row holds the `h1` screen title (plus, on the products screen only, the "Nuevo producto" link); the filter row, when rendered, sits directly below with its own `border-b` hairline; the table (or, on the analytics screen, the summary tiles and chart) follows. `AdminAnalyticsPage` has no filter row and no table — it's the simplest of the three, a header plus a `flex flex-col gap-8` stack of `AnalyticsSummaryTiles` and `TopSellingProductsSection` — but it reuses the identical outer shell rather than inventing a narrower one for a page with less content.

### Named Rules
**The Pinned Chrome Rule.** At the base/mobile breakpoint only, two pieces of checkout chrome pin to the viewport instead of scrolling with the page: `CheckoutStepIndicator` becomes `sticky top-0 z-10` (an `-mx-4` bleed back out to the viewport edge, `bg-bone dark:bg-ink`, and a `border-b border-ink/15 dark:border-bone/15` hairline so page content passes visibly underneath it), and the running total inside `CartLinesSummary` (when rendered with `totalVariant="sticky-bottom"`) becomes `fixed inset-x-0 bottom-0 z-10` with the same opaque `bg-bone dark:bg-ink` and a `border-t` hairline on the opposite edge. Both reset to normal in-flow positioning at `md:` and up — the step indicator becomes a static left-column list (`md:static md:mx-0 md:flex-col md:border-b-0 md:bg-transparent`) and the total sits inline above the step sections (`md:static md:mt-6 md:bg-transparent`), because there's room for both without competing with the viewport edge on desktop. This resolves a "decisión sin resolver" the surface's original direction contract left open for this build. **The pinning mechanism is always an opaque background plus a hairline border, never a shadow** — pinned chrome still obeys the Flat Ground Rule; it announces itself by covering content with a plane of the page's own ground color and a rule, not by lifting off the page.

## Elevation & Depth

Flat. No shadow, no gradient, and no blur exists anywhere in the sampled components. Depth is conveyed entirely by color-field contrast against the ink/bone ground — a bright flat field sitting on a near-black or bone page reads as "raised" without any actual shadow. Pinned/sticky-positioned chrome (see the Pinned Chrome Rule, under Layout) is the one place `position` itself changes to keep an element in view, and it still doesn't reach for a shadow to separate itself from the content passing beneath it — an opaque background plus a hairline border does that job instead.

### Named Rules
**The Flat Ground Rule.** Surfaces never lift with a shadow. If a component needs to stand out, it gets a field color, not an elevation. This holds even for `position: sticky`/`fixed` chrome (see the Pinned Chrome Rule) — pinning changes an element's position in the viewport, never its elevation.

## Shapes

Zero border-radius anywhere sampled — cards, image tiles, skeletons, the retry link, the filter controls, the cartela panel, the quantity stepper, `TextField`, `Button`, and the cart's line items and its remove/dismiss controls all have square corners. This is stricter than the direction contract's "no large rounded corners"; the shipped build has no rounded corners at all. Borders are hairline and low-opacity (`border-ink/15` in light, `border-bone/15` in dark) as the default — used on the header's bottom rule, the filter block's own bottom rule, the cartela panel (scoped to two edges only), `AuthPageLayout`'s and `CartPage`'s title/content dividers, `PaginationControls`' own top rule, and — as of slice 7a — both edges of the checkout's pinned chrome (`CheckoutStepIndicator`'s bottom rule, the sticky-bottom total's top rule) and the `md:` divider between the cart block and the step columns. **As of slice 13**, `AnalyticsSummaryTiles` reuses the identical `border-ink/15`/`dark:border-bone/15` hairline for its own `border-t` (opening the tile block off from the page header) and for the `sm:divide-x` rule between its two totals — the same low-opacity hairline vocabulary, applied to a vertical divider between two flowing values instead of a horizontal rule between sections, and `TopSellingProductsChart`'s own `CartesianGrid`/axis lines use the same `currentColor` at 15%/30% strokeOpacity, keeping the chart's own rules as faint as the rest of the system's hairlines rather than a heavier chart-library default. **As of slice 14**, `FeaturedProductHero`'s own outer `border-b border-ink/15 dark:border-bone/15` closes the hero block off from the catalog below it — the identical hairline weight, applied to a third kind of section boundary (hero-to-grid) after the header-to-content and filter-to-grid boundaries it already served. **One documented exception, now confirmed twice:** the catalog search input's resting-state border is `border-ink/50` (light) / `border-bone/40` (dark), deliberately heavier than the hairline default, to clear the binding WCAG 3:1 non-text contrast minimum for an interactive form control's resting boundary, which a hairline border cannot reliably meet. `TextField` reuses the identical values for the same reason — it is the same class of control (a bare bottom-border input with no fill), not a new exception invented for this build; `ShippingForm` and `PaymentForm` (slice 7a) reuse `TextField` unmodified, so this exception carries through to checkout without any new value. Treat this as a targeted exception for bare-bottom-border interactive-control boundaries, not a new default border weight — don't carry `ink/50`/`bone/40` into non-interactive hairlines elsewhere. `Button`, notably, does **not** use this heavier value: it has its own full border (`border border-current`) at full opacity, which already clears the same contrast floor without needing the `/50`/`/40` treatment — a bare-bottom-border control and a fully-bordered control solve the same accessibility requirement differently, and each should keep its own solution.

The dotted-rule spec table on the product detail page (`divide-y divide-dotted divide-ink/30`) is a second, distinct border vocabulary from the hairline solid rule used everywhere else — a punctuated, tabular divider rather than a structural edge. **Now confirmed in three contexts.** `CartPage`'s line-item list (`<ul>` of `CartLineItem`s) uses the identical `divide-y divide-dotted divide-ink/30 dark:divide-bone/30` class, and the cart skeleton mirrors it. `CheckoutPage` (slice 7a) reuses the same class a third time, for its column of step sections (shipping, payment, review) — a sequential-document divider rather than a tabular or itemized-list one, but the identical class, unchanged. Three genuinely distinct list shapes (spec/attribute pairs, receipt line items, document sections) now share one divider language; treat it as scoped to discrete, itemized-or-sequential vertical content, not a general alternative to the hairline convention for arbitrary content lists. **`AnalyticsSummaryTiles` deliberately does not reach for this dotted vocabulary** — two flowing totals are not an itemized or sequential list, so the plain hairline `border-t`/`divide-x` treatment (above) is the correct choice, not the dotted one. **Neither does `FeaturedProductHero`** — it has no itemized or sequential list of its own, just a name/note/price/CTA stack, so it has no occasion to reach for the dotted divider at all.

### Product Card

### Pagination Controls

### Featured Product Hero
`FeaturedProductHero` (`src/features/products/components/FeaturedProductHero.tsx`, slice 14, rendered by `CatalogPage` above the `id="catalogo"` filters/grid block) is the site's first hero, and it does not live on a separate landing route — the home page (`/`, `CatalogPage`) is hero-plus-catalog on one continuously-scrolling page, not two screens. Two-column grid at `md:` (one column below), the same field-colored-image-beside-a-bone-panel shape the product detail cartela already established: a `Link` to the product's detail page wraps the field-colored image panel on the left, and a `bg-bone text-ink` text panel on the right — unconditionally bone/ink, a second confirmed instance of the Fixed Paper Rule (see Colors) rather than the page's own theme-swapping ground. The panel holds the product name (`h2`, Display, `text-balance`), its `curatorialNote` in italic Body (the same field the cartela already reads, reused rather than any invented marketing copy — this is how F14.3's "no invented claims" requirement is satisfied, by construction, not by omission), price and `AddToCartControl` (both reused unmodified from the product detail page), and a plain in-page anchor, `href="#catalogo"` ("Ver el resto de la sala"), styled identically to the product-detail page's reviews link (`underline decoration-1 underline-offset-2`, theme-owned focus-visible ring, no hover-color treatment) — checked against that exact precedent during this slice's own `polish` pass and found to already match it byte-for-byte, not a new link style. Because there's no `scroll-behavior: smooth` anywhere in this codebase, the jump is instant, which trivially satisfies `prefers-reduced-motion` by having no motion to reduce.

The hero's `<img>` is the only image in this codebase using `loading="eager"`/`fetchPriority="high"` — every other product image (`ProductCard`, `ProductDetailPage`) is `loading="lazy"` — because this is the page's plausible LCP element and should not be deprioritized the way a below-the-fold image is.

**The hero's mobile image height genuinely diverges from the cartela's, and this is a confirmed, reasoned decision, not drift to reconcile.** The cartela's own image frame (`PRODUCT_IMAGE_FRAME_HEIGHT_CLASSES`, extracted to `src/features/products/constants/productImageFrame.ts` during this slice's `/simplify` pass, shared with `ProductDetailSkeleton` — see Product Detail Page) is `min-h-96 md:min-h-144` — a floor at every breakpoint, never a cap, which is correct there because nothing else on a single-item detail page competes with the image for viewport height. The hero does **not** import that constant: its own image frame is `h-64 md:h-auto md:min-h-144` — a genuine, fixed cap (256px) at the base/mobile breakpoint, floor-only from `md:` up. This was found and fixed during this slice's own live `polish` pass: at 320×800, the uncapped floor-only sizing let the image grow tall enough to push `AddToCartControl`'s "Agregar al carrito" button below the fold, violating F14.1/F14.2 (the CTA must be visible without scrolling). Capping the hero's mobile height was the fix, verified by measuring the CTA's bounding box before (786px top, cut off) and after (700px top, fully visible, 66px of margin). Don't "fix" the hero's `h-64` cap back to match the cartela's floor-only sizing — the two components share a visual family but not a viewport budget: the cartela can let its image grow because it owns the whole first viewport, the hero can't, because it shares that viewport with a CTA that has its own visibility requirement (see the new Do, below).

**No spec table**, unlike the cartela: the hero shows name, curatorial note, price, and the add-to-cart control only. This was a scoped decision made before writing any code, for the same reason slice 3 skipped "número de pieza y fecha de ingreso" from the same original brief — the schema allows up to 12 spec rows, which risked pushing the CTA off the first viewport even before the height-capping fix above. The full spec table remains exclusive to the product detail page, one click away via the hero's own links.

**Featured-product exclusion from the grid is conditional, not absolute.** `CatalogPage` only filters the featured product out of the array it passes to `ProductGrid` on the default view — no category filter, no search term, page 1, the one view where the featured product is guaranteed to be the grid's own first result under the catalog's default `createdAt desc` order. Under an active filter or search, the same product can legitimately reappear (e.g., searching for its own name) — that's correct search behavior, not a duplicate bug, so no exclusion applies there. If the exclusion would empty the grid but the catalog isn't actually empty (the featured product **is** the entire active catalog), `CatalogPage` omits the grid section — and `PaginationControls` — entirely, rather than showing a false "Todavia no hay productos" message; that empty-state copy is reserved for when Firestore's own result set is genuinely empty, not a post-exclusion display count of zero.

`useFeaturedProduct` (its data hook) and `useActiveProducts` (the grid's) are two independent `useKeyedAsync`-backed fetches with their own loading/error/success UI, not one combined query — the same deliberate independence slice 13's dashboard tiles/chart split already established, so a slow or failed featured-product read never blocks or delays the grid, and vice versa.

### Quantity Selector
A generic, reusable stepper (`src/components/ui/QuantitySelector.tsx`), not scoped to products. Two square `size-11` (44px) buttons flank a live-announced (`aria-live="polite"`) count; both buttons disable at their bound (quantity 1, or `maxQuantity`). **The border-current rule:** its step buttons use `border-current` rather than a hardcoded `border-ink dark:border-bone` pair. This was a real bug caught and fixed during the slice-3 build — a hardcoded `dark:border-bone` pair would render bone-on-bone and vanish inside the cartela in dark mode, because the cartela never theme-swaps (Fixed Paper Rule). Any component that may be placed inside a fixed-tone surface must use `currentColor` (or an explicit, non-conditional color) instead of a `dark:` variant tied to the page's own theme — the page's theme-swap cannot be assumed to reach every ancestor. **Confirmed reused in slice 5:** `Button` (below) independently follows the same `border-current`/`text-current` convention, for a related but distinct reason — not because it lives inside the cartela today, but so it stays safe to drop inside one later (checkout, admin forms) without a repeat of the QuantitySelector bug. **Confirmed reused in slice 6:** the component gained an optional `initialQuantity` prop (defaults to `1`, no visual change), its first consumer — `CartLineItem` seeds the stepper at the cart's stored quantity for that line instead of always starting at 1. `ProductDetailPage`'s existing usage via `AddToCartControl` is unaffected by the default. **Confirmed a third time in slice 14:** `FeaturedProductHero` renders inside its own second fixed-tone surface (see the Fixed Paper Rule) via the same `AddToCartControl`/`QuantitySelector` pairing the cartela already uses, unmodified — the exact case this rule was written to keep safe for.

### TextField
`TextField` (`src/components/ui/TextField.tsx`) is the labeled-input primitive behind every auth form, and — as of slice 7a — behind `ShippingForm` and `PaymentForm` as well. It's a `forwardRef` component (for `react-hook-form`'s `register()` to attach its ref directly) wrapping a Label-typography `<label>` and a bare bottom-border `<input>` — no fill, no box, the same "no boxes, just rules" language as the catalog search input, and it reuses that input's documented heavier resting border (`border-ink/50` / `dark:border-bone/40`) for the same WCAG 3:1 reason (see Shapes). On focus it swaps to the theme-owned accent, also matching the search input.

It takes an optional `hint` and an optional `error`, and the two share one `aria-describedby` slot rather than stacking: `hint` renders only when there's no `error`; when an `error` is present it takes over the slot and the hint disappears. This isn't an oversight — Zod's validation messages already restate the hint's content (e.g. the password-length rule), so showing both would double-announce the same information to screen reader users. `error` renders with `role="alert"` at 80%-opacity ink/bone text.

### Button
`Button` (`src/components/ui/Button.tsx`) is the primitive behind every form submit, the Google sign-in action, `PaginationControls`' "Anterior"/"Siguiente" controls, and — as of slice 7a — `ShippingForm`'s "Continuar a pago", `PaymentForm`'s "Revisar compra", and `ReviewSection`'s "Confirmar compra". Unlike most of the system's ink/bone-hardcoded text, it's built on `border-current`/`text-current` so it inherits whatever text color its container establishes — the same reasoning as the Quantity Selector's border-current rule, applied proactively so `Button` stays safe to drop inside a future fixed-tone surface without repeating that bug (confirmed again by slice 14's `FeaturedProductHero`, whose "Agregar al carrito" `Button` — via `AddToCartControl` — sits inside the hero's own fixed-tone panel without any change to the primitive). Its own border is a full `border border-current` (not the bare-bottom-border style of `TextField`/the search input), Label typography, uppercase, tracked. Hover/focus swap to the theme-owned accent (magenta light / cyan dark) on both border and text; disabled state drops to 40% opacity with `cursor-not-allowed` — this is the exact mechanism `PaginationControls` leans on for its first/last-page state, with no override or variant added. **As of slice 7a, `Button` exports its className string as `BUTTON_CLASSES`**, following the same pattern already established by `AUTH_NAV_LINK_CLASSES` (see Auth Navigation): `CartPage`'s "Ir a pagar" control is a `<Link>`, not a `<button>` (it navigates to `/checkout`, it doesn't submit anything), so it can't render through the `Button` component itself, but it can — and does — apply the exact same visual treatment by importing the exported constant instead of retyping the class string. `AdminProductsPage`'s "Nuevo producto" `<Link>` does the same. **`ReviewSection`'s "Confirmar compra" button is intentionally inert** — rendered through `Button` with no `onClick` at all. This is a disclosed, deferred-feature gap (order creation lands in a future slice), the same pattern the product detail page's "Agregar al carrito" button followed for several slices before slice 6 wired it up. Don't read the inert button as a defect to silently "fix" by inventing a stub handler; the deferral is the recorded state.

### InlineError
`InlineError` (`src/components/ui/InlineError.tsx`) is a tiny `role="alert"` message primitive, extracted after four forms independently duplicated the same markup for root-level (non-field) errors. It renders nothing when its `message` prop is falsy — callers pass the error straight through without an `if` guard at the call site. `PaymentForm` (slice 7a) reuses it for the "Resultado simulado" radio group's validation error. `AdminOrderRow` (slice 12) reuses it for a failed status-transition attempt, rendered beneath the row's action buttons.

### Auth Forms
`LoginForm`, `RegisterForm`, and `ForgotPasswordForm` are all built from `TextField` + `Button` + `InlineError` on `react-hook-form` with `zodResolver`, and all three share `mode: 'onTouched'` (validate on first blur, revalidate on every change after) — this is the established form-validation-timing convention for the codebase going forward, not a per-form choice. `ShippingForm` and `PaymentForm` (slice 7a) follow the identical `react-hook-form` + `zodResolver` + `mode: 'onTouched'` convention. Each form disables its whole `<fieldset>` (via `className="contents"`, so the fieldset doesn't introduce its own box) while submitting or redirecting, rather than disabling each field individually.

`RegisterForm` isolates its one live-computed value — whether the password is still too short to submit — into a small `RegisterSubmitButton` child component that subscribes with `useWatch({ control, name: 'password' })` rather than calling the form's whole-form-subscribing `watch()`. This keeps the re-render caused by every keystroke scoped to the submit button alone instead of the entire form; it's the pattern to reuse for any future form that needs a live-computed disabled/enabled state, given this project's stated performance-sensitivity brief.

### Checkout Page
`CheckoutPage` (`src/features/checkout/pages/CheckoutPage.tsx`, slice 7a, route `/checkout`, inside `PrivateLayout`/`ProtectedRoute` — checkout requires an authenticated session, unlike the cart) opens with the same `<h2>` "Checkout" title pattern as `CartPage`, then renders `CartLinesSummary` with `totalVariant="sticky-bottom"` (see the Pinned Chrome Rule, under Layout). There is no per-step route, no modal, and no screen swap: the cart and all three steps are one continuously-scrolling document, visually separated only by the dotted rule between sections. Checkout draft state (shipping details, payment draft, which step is active) persists per-uid, the same durable-draft pattern the codebase already uses elsewhere for per-user client state.

### Checkout Step Indicator
`CheckoutStepIndicator` (`src/features/checkout/components/CheckoutStepIndicator.tsx`) is the three-item step nav (Envío, Pago, Revisión), rendered as an `<ol>`. Each step renders in exactly one of three states, and the three states are the whole vocabulary — there is no fourth: 
- **Completed** (its form has been submitted): a clickable `<button>`, Label typography, underlined (`underline decoration-1 underline-offset-2`), full-opacity ink/bone text, theme-owned accent on hover/focus — clicking it calls back into the draft's `editShipping`/`editPayment` to return to that step's form.
- **Active** (the step currently showing its form): a plain `<span>`, Label typography, full-opacity ink/bone text, with a heavier accent-colored underline (`decoration-field-magenta decoration-2` / `dark:decoration-field-cyan`) that doesn't change on hover because it isn't interactive.
- **Unreached** (a later step not yet visible): a plain `<span>`, Label typography, dimmed to 40% opacity ink/bone, not interactive.

**Step navigation is backward-only by construction, not by a `disabled` attribute.** "Revisión" never renders as a `<button>` under any state — there is no state in which it's editable directly, matching the review step's role as a read-only summary of the other two. An unreached step is a plain dimmed label, never a `disabled` `<button>`, following the same reasoning as `PaginationControls`' "can't go further" treatment but expressed as a non-interactive element instead of a disabled interactive one, because an unreached step isn't a control that temporarily can't be pressed — it's not a control at all yet. At the base breakpoint the `<ol>` itself is the pinned chrome described in the Pinned Chrome Rule (`sticky top-0`, horizontal `flex gap-6` layout); at `md:` and up it resets to a static vertical list (`md:flex-col md:gap-4`) in the page's left column. **Confirmed a third time in slice 12:** `AdminOrderRow` applies the identical "not a control yet, not a disabled control" reasoning to its own transition buttons — see Admin Orders Table.

### Checkout Forms
`ShippingForm` and `PaymentForm` (`src/features/checkout/components/`) are `react-hook-form` + `zodResolver` forms built from `TextField` + `Button`, following the exact `mode: 'onTouched'` and whole-`<fieldset>`-disable convention established by the auth forms (see Auth Forms) — no new form-validation-timing decision was made for checkout. `ShippingForm` collects name, address, city, postal code, and phone (each a `TextField`), submitting to "Continuar a pago". `PaymentForm` deliberately collects only a cardholder name plus a native radio-button choice between "Aprobado" and "Rechazado" under a "Resultado simulado" `<fieldset>`/`<legend>` — **no card number, expiry, or CVV field exists**, and a `text-xs`/70%-opacity disclosure line states plainly that no real charge is processed. This is a scoped simplification confirmed by finish review: the spec requires only the ability to force a success/failure outcome for testing the flow, not a realistic card-entry form, so building fake card fields would be simulating security theater the surface doesn't need. The radio group's validation error renders through the shared `InlineError` primitive, not a bespoke fieldset-level error style.

### Checkout Summary Card
`CheckoutSummaryCard` (`src/features/checkout/components/CheckoutSummaryCard.tsx`) is the shared shell behind `ShippingSummary` and `PaymentSummary`: a Display-typography title on the left, an "Editar" text control on the right (Label typography, underlined, theme-owned accent on hover/focus — the identical visual treatment as `CheckoutStepIndicator`'s completed-step buttons, not a second style invented for the same action), and a `children` slot underneath the title for the step's confirmed values (Body type, 80%-opacity ink/bone — see Typography). ### Review Section
`ReviewSection` (`src/features/checkout/components/ReviewSection.tsx`) is the final, always-read-only step: a Display "Revisión final" title, a Body-type confirmation line restating the total (reusing the shared `formatPrice` utility, not a new formatter), and a `Button` labeled "Confirmar compra". **That button is intentionally inert** — it renders through the stock `Button` primitive with no `onClick` at all, because order creation is out of scope for this slice (see Button, above, for the disclosed precedent this follows). `ReviewSection` never renders a form and never has an "Editar" control of its own; there's nothing to summarize back into a form because it doesn't hold any of its own state — it only reads the shipping and payment drafts already confirmed by the two steps above it.

### Modal
`Modal` (`src/components/ui/Modal.tsx`, slice 8) is this system's first overlay primitive: an opaque `bg-ink/60` backdrop behind a `bg-bone`/`dark:bg-ink` panel with a hairline border — never a shadow, the same Flat Ground Rule the rest of the system already holds to, just applied to an element that finally sits above the page instead of in its flow. `role="dialog"`/`aria-modal="true"`/`aria-labelledby` point at a Display-typography `<h2>` title; focus traps inside the panel, Escape and a backdrop click both close it (disable-able via `closeDisabled` while a destructive action is mid-flight), and focus returns to the element that opened it on close. Initial focus lands on whichever element the caller passes as `initialFocusRef` — every current consumer (see Confirm Action Modal) points this at the safe "Volver" control, not the destructive one, so a reflexive Enter can never confirm a destructive action by accident. Built for reuse from the outset, not a one-off: three destructive-confirmation flows were already planned for later slices when this shipped, and a fourth — this slice's own admin order cancellation — is the one that confirmed it.

### Confirm Action Modal
`ConfirmActionModal` (`src/components/ui/ConfirmActionModal.tsx`) is the shared shell behind every destructive-confirmation flow in this system: a `Modal` (see above) whose body is caller-supplied text naming exactly what's being destroyed — never a bare "¿estás seguro?" — closed by a safe "Volver" text control and a destructive `Button` labeled with the caller's own verb ("Confirmar cancelación", "Borrar reseña", "Eliminar definitivamente"). It owns the async submit state itself: a failed `onConfirm` shows its message inline (via `InlineError`, `aria-live="polite"`) without closing the modal, preserving context instead of losing the user's place; a successful one calls `onConfirmed` and lets the caller close it. Extracted during slice 9's `/simplify` pass once slice 8's one-off `CancelOrderModal` and slice 9's new `DeleteReviewModal` turned out to be the identical shell around two different verbs — both are now thin wrappers supplying only `title`/`body`/`confirmLabel`/`onConfirm`.

Its trigger, `DestructiveTriggerButton` (`src/components/ui/DestructiveTriggerButton.tsx`), is a Label-typography underlined text control — no button chrome, matching the system's retry-link/"Quitar" visual language rather than a filled destructive button — reused by `OrderDetailPage`'s "Cancelar orden", `ProductReviewsPage`'s "Borrar mi reseña", and — as of slice 12 — `AdminOrderRow`'s own "Cancelar" per-row trigger. **`CancelOrderModal`'s prop shape changed in slice 12**, from taking a `user` prop and calling `cancelOrder` internally to taking an injected `onCancel: () => Promise<Result>` action instead: the customer's own order-detail page passes a call scoped to the signed-in customer, and `AdminOrderRow` passes a call to the admin status-update endpoint — the same modal, two different backing actions, neither hardcoded inside it anymore. **`DestructiveTriggerButton` also gained a `disabled` prop this slice** (used while a row's transition request is in flight) and now exports its class string as `TEXT_ACTION_BUTTON_CLASSES` — reused, unmodified, by `AdminOrderRow`'s non-destructive forward-transition buttons ("Marcar en proceso", "Marcar completada"). This is a case of a destructive-only-named component becoming the shared visual base for a same-language but not-destructive sibling action: the component's name still describes its original, still-current purpose (opening a destructive confirmation), while the exported class constant is the reusable piece, the same "export the className, not the component" move `Button`'s `BUTTON_CLASSES` already established.

### Admin Products Table
`AdminProductsPage` (`src/features/admin/products/pages/AdminProductsPage.tsx`, slice 10, route `/admin/products`) is the surface brief's THESIS made literal: "la tabla es la pantalla, no un componente dentro de la pantalla." It fetches the full product catalog once — no `isActive` filter, unlike the public catalog's `getActiveProducts`, because a retired product has to stay visible here to be reactivated — and filters client-side by category and name, instantly, with no debounce. This is a deliberate divergence from the public catalog's 400ms-debounced Firestore query: there's no network cost left to debounce against once the full list is already in memory, and an operator correcting prices all day is better served by an instant filter than a delayed one.

A real `<table>` at `md:` and up; below that, each `AdminProductRow`'s `<tr>` becomes a `flex flex-col` stacked card and every `<td>` an inline `flex justify-between` row carrying its own `md:hidden` field label — never a horizontal scroll, per the brief's binding constraint. Those inline labels, and the desktop `<th>` row, share one class, `TABLE_LABEL_CLASSES` — **as of slice 12, relocated to `src/features/admin/constants/tableLabelClasses.ts`**, since a second admin sub-feature (orders) now needs the identical string; it no longer lives under `products/`. Label typography at 60%-opacity ink/bone. **A real contrast defect, caught and fixed during this slice's own finish-review pass:** the first draft used `/50`, an opacity never used for text anywhere else in this system (only ever documented as a *border* exception, for the search input/`TextField`) and measured at roughly 3.5:1 against bone — below the 4.5:1 AA floor for text this size. `/60`, the value already carrying the category-rail chip's inactive state, measures at roughly 4.8:1 and was substituted in its place. The empty state and the "filter matched nothing" state (F9.9/F9.10) are two different `EmptyState` calls with different copy, the same empty-vs-filtered distinction the public catalog already draws. **As of slice 12**, its loading state renders the shared `TableSkeleton` (see below) rather than a products-specific skeleton.

### Admin Orders Table
`AdminOrdersPage` (`src/features/admin/orders/pages/AdminOrdersPage.tsx`, slice 12, route `/admin/orders`) reuses the Admin Products Table's shape exactly, down to the page shell (`mx-auto max-w-6xl px-4 py-10 md:px-8 lg:px-12`), the real `<table>`-at-`md:`/stacked-card-below-it split, the `TABLE_LABEL_CLASSES` column labels, and `TableSkeleton` for loading — no new table visual language was built for a second admin table. `AdminOrderFilters` reuses `FILTER_CHIP_CLASSES` for its status chips (see Catalog Filters). **Its one deliberate divergence from its sibling, per F11.2:** the status filter lives in the URL (`?status=`), parsed defensively through `parseOrderStatusParam` (an invalid or stale query value falls back to "no filter" rather than erroring), not client-only `useState` like `AdminProductsPage`'s category/name filter — a shareable/bookmarkable/back-button-safe filter for an operational view where "show me only pending orders" is a state worth linking to, unlike the product table's instant free-text search.

This is the same "not a control yet, not a disabled control" philosophy `CheckoutStepIndicator` already established for its unreached steps, now confirmed a third time for a different kind of state machine (an order's lifecycle status instead of a form's step progression). The two forward transitions ("Marcar en proceso", "Marcar completada") are direct one-click actions with no modal — reversible in the sense that a later admin action can move the order further, matching the precedent `AdminProductRow`'s retire/reactivate toggle already set for non-destructive admin actions. Only "Cancelar" opens `CancelOrderModal` (see Confirm Action Modal): it's the one transition that reverses stock and product counters, so it gets the same destructive-confirmation treatment as every other irreversible action in this system. A failed transition attempt (of either kind) shows its message through `InlineError` beneath the row's action buttons, and never removes or disables the row itself.

### Editable Number Cell
`EditableNumberCell` (`src/features/admin/products/components/EditableNumberCell.tsx`, slice 10) is the price/stock inline editor: a bare bottom-border `<input type="number">` — the same no-fill, no-box language as `TextField`/the catalog search input, reusing their documented `border-ink/50`/`dark:border-bone/40` resting-border exception — that commits on blur or Enter, `tabular-nums` throughout. On a failed save it reverts to the last confirmed value and explains the error underneath, in place; there is no shared or global saving flag anywhere in the row, a `savingId`-per-row model the surface brief calls for by name. It's keyed by its own `value` prop (`key={product.price}`) rather than carrying manual resync logic: a save that lands elsewhere in the table (another row's retire, a hard-delete) refetches the whole list, and any row whose true value actually changed remounts cleanly to the fresh number — but the row that made its own edit never remounts, because by the time a remount could fire, the value it already holds locally already matches what came back from the server. A save never costs focus this way, satisfying the brief's "el foco no se pierde al guardar una celda" without any explicit focus-management code.

### Admin Analytics Page
`AdminAnalyticsPage` (`src/features/admin/analytics/pages/AdminAnalyticsPage.tsx`, slice 13, route `/admin/analytics`) is the third and final admin sub-screen (F12), and the first admin surface with neither a filter row nor a table. It's gated on a single hook, `useOrdersSummary` (one Firestore aggregation query — `sum('total')` + `count()` over non-cancelled orders, not a client-side reduction over every order document): a `AnalyticsSummaryTilesSkeleton` while loading, `ErrorState` on failure, and — the one page-level branch specific to this screen — a single `EmptyState` ("Todavía no hay ventas") in place of **everything** below the `h1` when `summary.totalOrders === 0`. Only once `totalOrders > 0` does the page render `AnalyticsSummaryTiles` and `TopSellingProductsSection` together in a `flex flex-col gap-8` stack. This whole-page empty gate is a deliberate choice, not a shortcut: a page with a populated `EmptyState` up top and an empty chart underneath it would show the same "nothing to see" fact twice, once in prose and once as a blank chart — the page says it once, and says nothing else.

`TopSellingProductsSection` is a second, independent async unit below the tiles, with its own hook (`useTopSellingProducts`), its own `TopSellingProductsChartSkeleton`, and its own `ErrorState`+retry — **deliberately not merged into one fetch with the summary**, so a failure in the ranking query (or a slow one) never blocks or delays the revenue/order-count tiles, and vice versa. It also handles its own `products.length === 0` case with a plain `text-sm`/70%-opacity inline sentence ("Todavía no hay unidades vendidas para armar el ranking") rather than a second `EmptyState` — defense-in-depth alongside the page-level empty gate above it, for the edge case where orders exist (so the page-level gate doesn't fire) but none of them have yet incremented any product's `unitsSold` (F12's ranking source explicitly excludes 0-unit products via `where('unitsSold','>',0)`, so it's never populated with a false "top seller").

### Analytics Summary Tiles
`AnalyticsSummaryTiles` (`src/features/admin/analytics/components/AnalyticsSummaryTiles.tsx`, slice 13) shows "Ingresos totales" and "Cantidad de órdenes" as two label/value pairs inside one flowing `<dl>` — **not** a pair of boxed metric-card tiles. ### Top Selling Products Chart
`TopSellingProductsChart` (`src/features/admin/analytics/components/TopSellingProductsChart.tsx`, slice 13) is this project's first chart, built on Recharts (`recharts@^3.10.1`, first charting dependency in this codebase). A single horizontal `BarChart` (`layout="vertical"`), one series — units sold, top five products, sourced with `where('unitsSold','>',0)` so a never-sold product can never appear as a false "top seller." Every color prop Recharts exposes (`Bar fill`, `LabelList fill`, both axes' `tick.fill`, both axes' and the grid's `stroke`) is set to `currentColor`; the chart's own wrapping `<div>` sets `text-ink dark:text-bone`, so the entire chart — bars, labels, axis ticks, gridlines — inherits the page's theme-swap the same way every other component in this system does, with zero chart-specific color tokens added to the palette. The `CartesianGrid`/axis strokes additionally match this system's existing hairline weight (`strokeOpacity` 0.15/0.3, see Shapes) rather than a heavier chart-library default. Each bar's exact value is drawn directly on the bar via `LabelList` (`position="right"`), not left to a hover-only tooltip — no series in this chart depends on color, or on a pointer interaction, alone to be read. **`isAnimationActive={false}`** is a deliberate choice, not an omission: no entry animation exists anywhere else in this system (skeletons pulse, nothing else moves), so the chart's one Recharts-default animation is switched off to match that "no motion for its own sake" register; Recharts' `accessibilityLayer` (on by default in v3) still gives the chart keyboard navigation and screen-reader semantics despite carrying no animation. `TopSellingProductsChartSkeleton` is a single flat `motion-safe:animate-pulse` block at the chart's own `h-64` height — it doesn't attempt to mirror bar shapes, the same reasoning `TableSkeleton` already established for not over-fitting a generic loading placeholder to structured content it can't predict in advance.

## Do's and Don'ts

### Do:
- **Do** assign exactly one of the four closed field colors, full-strength and full-bleed, per product tile — and, on the product detail page and the catalog's featured-product hero, to the image panel itself, and, on the cart page, to each `CartLineItem`'s color stripe.
- **Do** keep Bodoni Moda to one headline-weight string per component (name, price, or state message) — never stack two didone lines competing for attention within the same component, even on a continuously-scrolling document like checkout or the catalog-with-hero home page where several components each carry their own single headline.
- **Do** build any new skeleton to the exact shape of its loaded content, and gate its animation behind `motion-safe:` — unless the loading target is a generic dense table (see `TableSkeleton`) or chart (see `TopSellingProductsChartSkeleton`) with no fixed column/series shape worth mirroring, in which case a shared flat block is the right call, not a per-consumer one.
- **Do** source interactive accent color from the active theme (magenta light / cyan dark), not a hardcoded hex — except inside a fixed-tone surface (the cartela, and — as of slice 14 — the catalog's featured-product hero), where hardcoded `ink`/accent colors are correct because that surface never swaps.
- **Do** keep corners square and surfaces shadow-free; depth comes from the field color, never from elevation.
- **Do** cycle small color swatches (category-rail dots, product `displayColor`, the cart line-item stripe) through the closed four-field set by index, and let the adjacent text label do the disambiguation — repeated colors across items are expected, not a bug to fix with a fifth color.
- **Do** keep a filter/text control that needs to clear the WCAG 3:1 non-text UI-boundary floor on a heavier border than the system's default hairline, scoped to that control's bare-bottom-border style (`ink/50`/`bone/40`) — a fully-bordered control like `Button` can clear the same floor with its own full-opacity `border-current` instead.
- **Do** use `border-current`/`currentColor` (not a `dark:` variant) in any reusable component that might be dropped inside a fixed-tone surface like the cartela or the featured-product hero — see the Quantity Selector's and `Button`'s border-current rule. Any future chart, SVG, or third-party-library component follows the identical reasoning by using `currentColor` for every color prop it exposes, as `TopSellingProductsChart` already does.
- **Do** use `aria-labelledby` referencing separate name/description/price node ids for card-as-link components, following the Product Card's pattern, rather than a single flattened `aria-label`.
- **Do** validate forms with `react-hook-form`'s `mode: 'onTouched'` and isolate any live-computed, per-keystroke UI state (e.g. a disabled submit button) into a small child component subscribed with `useWatch`, not the form's whole-subscribing `watch()`.
- **Do** share one `aria-describedby` slot between a field's hint and its error (hint hidden once an error is present) rather than stacking both, when the error message already restates the hint's content.
- **Do** reuse the stock `Button` primitive and its existing `disabled` treatment for prior/next-style controls (see `PaginationControls`) instead of building a bespoke state for "can't go further" — 40% opacity plus `cursor-not-allowed` already says it.
- **Do** reuse the dotted-rule divider (`divide-dotted`) for itemized receipt-style lists and sequential document sections (see `CartPage`'s line-item list and `CheckoutPage`'s step sections), alongside its original `<dl>` spec-table use — it is now a confirmed three-context pattern, not a one-off.
- **Do** render a label-plus-count control (see `CartIndicator`) as a single interpolated string inside one text node, not a label text node followed by a separately-rendered count span — splitting them collapses the space in the browser's accessible-name computation.
- **Do** export a primitive's className string as a named constant (see `Button`'s `BUTTON_CLASSES`, `AuthNav`'s `AUTH_NAV_LINK_CLASSES`, `DestructiveTriggerButton`'s `TEXT_ACTION_BUTTON_CLASSES`, `AnalyticsSummaryTiles`' `ANALYTICS_SUMMARY_CLASSES`, `FeaturedProductHero`'s `FEATURED_PRODUCT_HERO_LAYOUT_CLASSES`) when a non-primitive element, a same-visual-but-different-semantics sibling control, or that component's own skeleton needs to look identical to the original without duplicating its class string.
- **Do** use `position: sticky`/`fixed` with an opaque `bg-bone`/`dark:bg-ink` background and a hairline border (never a shadow) when pinning navigational chrome or a running total at the base/mobile breakpoint — see the Pinned Chrome Rule. Reset to normal in-flow layout at `md:` and up once there's room for the chrome to sit statically instead of competing with the viewport edge.
- **Do** render a completed multi-step form's step as a clickable, non-disabled control (a `<button>`) and an unreached step as a plain, non-interactive dimmed label (a `<span>`), not a `disabled` `<button>` — an unreached step isn't a control that's temporarily unavailable, it's not a control yet at all (see `CheckoutStepIndicator`). The same reasoning governs which action buttons render on a row bound to a state-machine graph (see `AdminOrderRow`'s `ORDER_STATUS_TRANSITIONS`-gated buttons): a transition the graph doesn't allow from the current state isn't rendered, disabled or otherwise.
- **Do** use one of the system's own verified text-opacity steps — `/60`, `/70`, `/80` — for de-emphasized ink/bone text, never a fresh value picked by eye. `/50` is documented and verified only as a *border* exception (the search input/`TextField`'s resting boundary); at text weight it measures below the 4.5:1 AA floor (see Admin Products Table, under Components, for the slice-10 instance this caught).
- **Do** use `Controller`, not `register()`, for any radio or checkbox group bound to a non-string field (see `RatingInput`) — `register()`'s own uncontrolled-group sync compares `defaultValues` against the DOM's string `value` attribute and silently fails to pre-check the right option when the field is a number.
- **Do** compute a live summary (a rating average, a count) from a list already loaded in memory rather than from a denormalized field on a parent document, when the screen holds that list anyway (see `ProductReviewsPage`) — it's both more accurate and the only way the summary updates without a reload, without depending on a server-side recalculation's timing.
- **Do** key a self-contained editable control by the external value it displays (see `EditableNumberCell`'s `key={product.price}`) when the control needs to resync to a value that can change from outside its own edits, without hand-written resync logic — the control's own optimistic edit never remounts itself this way, because the key only changes when the true value diverges from what the control already holds.
- **Do** lift an async sub-flow's busy state (a file upload, a secondary fetch) into the parent form when the form's own submit gate has to account for it (see `ImageUploadField`/`useImageUpload`, called from `AdminProductForm`) — a child component that only disables itself lets the parent submit mid-flight with stale data. Keep any presentational sub-piece a pure function of props (`state`, not a hook it owns) so the parent stays the single source of truth for what counts as "busy."
- **Do** inject a caller-supplied async action into a shared confirmation modal (see `CancelOrderModal`'s `onCancel` prop, slice 12) rather than hardcoding one internal call plus a `user`/context prop, once a second caller needs to supply a differently-scoped action through the identical modal shell — this keeps `ConfirmActionModal`'s whole lineage (`CancelOrderModal`, `DeleteReviewModal`) reusable across roles, not just across products.
- **Do** put an admin table's own filter state in the URL only when the surface brief actually calls for a shareable/bookmarkable filter (see `AdminOrderFilters`' `?status=`) — a filter with no such requirement (see `AdminProductFilters`' client-only category/name state) stays local state; the two admin tables are allowed to diverge on this by design, not by oversight.
- **Do** show a small set of admin summary totals (two to a handful of numbers) as a flowing `<dl>` — label/value pairs separated by a hairline `border-t`/`divide-x`, Label-weight `<dt>`, Display-weight `<dd>` — never as a grid of individually bordered metric-card tiles (see Analytics Summary Tiles, and `OrderDetailPage`'s subtotal/shipping/total block, the pattern's first instance). A boxed metric card reads as the generic product-analytics-dashboard template this admin surface's own THESIS explicitly rejects; the flowing list is this system's own established alternative, not a new invention to reach for each time.
- **Do** keep independent data sections of a dashboard-adjacent page (see `AdminAnalyticsPage`'s summary tiles and `TopSellingProductsSection`, and — as of slice 14 — the catalog page's featured-product hero and its product grid) on separate hooks/queries with their own loading/error/empty handling, rather than merging them into one fetch — one section's failure or slowness should never block or delay a sibling section that doesn't depend on it.
- **Do** let a component that reuses another's exact visual proportions diverge from them when the two share a visual family but not a viewport budget (see `FeaturedProductHero`'s capped `h-64` mobile image height versus the cartela's floor-only `min-h-96`) — a shared visual language doesn't require identical sizing forever if one consumer carries a competing element (here, a CTA with its own fold-visibility requirement) that the other doesn't. Verify the divergence with an actual measurement (a bounding-box check at the real viewport in question), not by eye, before recording it as intentional.
- **Do** exclude a page's own featured/pinned item from a list rendered beneath it only for the default, unfiltered view where duplication is guaranteed (see `CatalogPage`'s conditional `featuredIdToHide`) — under an active filter or search, let the item reappear if it legitimately matches; that's correct filtering behavior, not a duplicate to suppress. And when the exclusion would leave a non-empty source list looking empty, omit the downstream section entirely rather than showing the list's genuine "nothing here" empty state for a display-count-of-zero that isn't the same fact.

### Don't:
- **Don't** add border-radius, drop shadows, gradients, or glassmorphism — none exist in the shipped system and none are implied by the direction contract.
- **Don't** introduce a tint, opacity variant, or fifth color into the closed four-field set — including as a "fix" for a category or product that happens to share a cycled swatch color with another.
- **Don't** assume the catalog's hero (slice 14) lives on a separate landing route, or that it renders a full dotted spec table the way the cartela does — `FeaturedProductHero` is a section of `CatalogPage` itself (`/`, one continuously-scrolling page), and it deliberately shows only name, curatorial note, price, and add-to-cart, not the spec table (see Featured Product Hero, under Components).
- **Don't** treat the current light theme (a literal ink/bone swap) as the finished "separately designed" light mode the direction contract calls for — it is recorded here as shipped behavior, not as an approved target for future light-theme work.
- **Don't** generalize the search input's/`TextField`'s heavier border (`ink/50`/`bone/40`) into the system's default border weight — it's a one-off floor for bare-bottom-border interactive controls' resting-state contrast, not a replacement for the hairline (`ink/15`/`bone/15`) convention used everywhere else.
- **Don't** fold catalog-specific filtering controls into `PublicLayout`'s shared header — it also wraps routes (product detail, auth pages, cart) that don't need them; keep filter UI on the routes that use it.
- **Don't** generalize the Fixed Paper Rule into a third fixed-tone surface without the same editorial reason (a physical paper specimen object in the scene) — it is a named exception, now confirmed twice (the cartela, and — as of slice 14 — the catalog's featured-product hero); the slice-5 auth pages, the slice-6 cart page, and the slice-7a checkout page all confirm the boundary by deliberately staying on the page's own theme-swapping ground instead, even where they pin chrome to the viewport edge.
- **Don't** wire a hardcoded `dark:` color pair onto a component that could end up inside a fixed-tone surface; use `currentColor`/`border-current` or an explicit non-conditional value instead.
- **Don't** treat the product detail page's two `<h1>` elements (header wordmark + cartela name) as a pattern to reproduce deliberately elsewhere — it's a disclosed, single-item-page trade-off, not a system-wide heading convention. `AccessDeniedState`, `CartPage`, `CheckoutPage`, and — as of slice 14 — `CatalogPage`'s own featured-product hero (an `h2`, not a second `h1`) all keep to the strict one-`h1`-per-page rule for exactly this reason.
- **Don't** read `PaginationControls`' small `text-xs` page-label caption as a precedent for a new uppercase/tracked "kicker" or eyebrow treatment — it is plain Body-family support text at a smaller size (matching `TextField`'s hint), not the Label token, and no kicker/eyebrow component exists anywhere in this system.
- **Don't** nest a `<button>` inside an `<a>` (or vice versa) — invalid HTML. When a card or list item needs both a navigation link and an independent action (see the Product Card's slice-6 quick-add button), wrap both in a container element and keep the interactive controls as siblings, not nested.
- **Don't** use a `disabled` `<button>` to represent an unreached step in a multi-step flow, or a not-yet-valid transition on a state-machine-backed row — render it as a plain non-interactive element, or simply don't render it at all (see `CheckoutStepIndicator` and, as of slice 12, `AdminOrderRow`'s per-status transition buttons); a `disabled` control implies the action exists but is temporarily blocked, which isn't true for a step or transition that isn't reachable yet.
- **Don't** treat the payment step's absence of a card-number/expiry/CVV field as a gap to "complete" — it's a confirmed, scoped simplification (the spec requires only a forceable success/failure outcome, not a realistic card form); adding fake card fields would add fields the spec never asked for without adding any real capability.
- **Don't** wire up `ReviewSection`'s "Confirmar compra" button with a stub handler to make it "feel" functional — the inert button is the disclosed, correct state for this slice; order creation is deferred, and inventing a fake success path would misrepresent what actually ships.
- **Don't** read `AdminOrderFilters`' URL-based status filter as the new default for every admin filter — it's a deliberate divergence from `AdminProductFilters`' client-only state, made because F11.2 explicitly calls for a shareable status filter; don't retrofit URL state onto the product table's filter without an equivalent requirement.
- **Don't** render a small set of admin summary numbers as a bordered grid of metric-card tiles (a box per number, label-then-big-number inside it) — this was tried for `AnalyticsSummaryTiles` and reverted during finish review specifically because it reads as the generic product-analytics-dashboard aesthetic this admin surface's own direction contract THESIS rejects by name. It never shipped past that review and is recorded here only as the device to keep rejecting, not as a defect anyone still needs to fix — use the flowing `<dl>` pattern instead (see the Do above, and Analytics Summary Tiles).
- **Don't** "fix" `FeaturedProductHero`'s capped `h-64` mobile image height back to the cartela's floor-only `min-h-96` — the two intentionally diverge (see Featured Product Hero, under Components, and the new Do above); matching them again would silently reopen the below-the-fold CTA defect this slice's own `polish` pass found and fixed.
